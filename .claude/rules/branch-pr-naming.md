# 브랜치·PR 이름 규칙 — 목록만 보고 무엇을 하려던 것인지 알 수 있게 한다

> 한 줄 요지: **브랜치 이름은 `<종류>/<영문-슬러그>`, PR 제목은 `<종류>: <한 문장>`이고, 그 한 문장의 요지는 앞 40자 안에 들어간다.** 그리고 **세션은 브랜치를 스스로 만들지 않는다** — 만들어야 하면 이름을 먼저 보여 주고 승인을 받는다.

여기서 "브랜치"는 git 의 작업 가지를, "PR"(풀 리퀘스트)은 그 가지를 `main` 에 합쳐 달라는 요청을 말한다. 이 규칙은 둘의 **이름**만 정한다. 언제 머지하느냐 같은 절차는 [머지 게이트](../commands/merge-gate.md)와 각 저장소의 `CLAUDE.md` 가 정한다.

## 왜 이 규칙이 있나

이름이 제각각이면 **쌓인 뒤에 지워도 되는지조차 판단할 수 없다.** 한 저장소에서 실측하니 원격에 브랜치 87개가 있었고 그중 58개는 이미 머지된 채 남아 있었는데(2026-09-16), 대부분이 `claude/fervent-pasteur-y2g5wr` 처럼 무엇을 하려던 것인지 이름으로 알 수 없는 것이었다. 지우려면 하나씩 열어 diff 를 읽어야 하고, 그 비용 때문에 아무도 지우지 않아 계속 쌓인다.

PR 제목도 같은 문제를 다른 자리에서 낸다. GitHub 의 PR 목록은 제목을 잘라 보여 주므로, 요지가 뒤에 있으면 **목록에서는 그 PR 이 무엇인지 보이지 않는다.** 실제로 `2026-09-22 에 마이그레이션 적용 절차에 따라 project_task 표에…` 로 시작하는 제목이 목록에서 통째로 잘려, 연 사람조차 무엇인지 알아보지 못한 일이 있었다.

## 1. 브랜치 이름 — `<종류>/<영문-슬러그>`

```
feat/project-group-gen
fix/gen-task-order
mig/project-task-created-at
```

- **종류**는 아래 여섯 중 하나다. 더 만들지 않는다 — 종류가 늘면 고르는 데 시간이 들고 목록에서 묶어 보는 이득이 사라진다.

  | 종류 | 언제 |
  |---|---|
  | `feat` | 새 기능·새 화면 |
  | `fix` | 동작이 잘못된 것을 고칠 때 |
  | `mig` | 데이터베이스 마이그레이션이 들어갈 때 |
  | `refactor` | 동작을 바꾸지 않고 구조만 바꿀 때 |
  | `docs` | 문서·규칙만 바뀔 때 |
  | `chore` | CI·설정·의존성처럼 제품 밖의 것 |

- **슬러그**는 영문 소문자와 하이픈으로 **두세 낱말**이다. 무엇을 하는지가 드러나야 한다 — `fix/bug` 는 슬러그가 아니다.
- **PR 번호를 이름에 요구하지 않는다.** 번호는 PR 이 생겨야 존재하므로 요구하면 "브랜치를 만들고 → PR 을 열고 → 번호를 알아내 → 브랜치 이름을 바꾸는" 춤이 따라온다. 실제로 그 이름 바꾸기가 **열려 있던 PR 을 닫아 버린 일**이 있었다(2026-09-21) — GitHub 의 브랜치 이름 변경이 초안 PR 을 따라오지 않았고 다시 열 수도 없었다. 번호를 넣고 싶으면 `feat/409-project-group-gen` 처럼 **PR 을 연 뒤 처음부터 그 이름으로 만드는** 경우에만 넣는다.
- **대괄호를 쓰지 않는다.** `[#PR 409]` 같은 형태는 git 이 브랜치 이름으로 받지 않는다(`[` 는 ref 에 금지된 문자다).

## 2. PR 제목 — `<종류>: <무엇을 하는지 한 문장>`

```
feat: GEN 단계를 관문에서 서랍으로 바꾼다
fix: 태스크 줄 순서가 고칠 때마다 바뀌던 것을 고정한다
mig: project_task 에 created_at 을 더한다
```

- **종류는 브랜치와 같은 것**을 쓴다. 둘이 다르면 어느 쪽이 맞는지 읽는 사람이 판단해야 한다.
- **한 문장은 "무엇을 하는지"를 평서형으로** 쓴다. `~함`·`~수정` 같은 명사 끝맺음보다 `~로 바꾼다`·`~을 고정한다` 가 읽힌다.
- **요지가 앞 40자 안에 들어가야 한다.** 목록에서 잘리는 자리가 거기다. 날짜·이슈 번호·절차 이름 같은 것을 앞에 두지 않는다 — 그것들은 본문에 적는다.
- **제목에 PR 번호를 넣지 않는다.** GitHub 이 제목 옆에 이미 붙여 준다.

## 3. 세션은 브랜치를 스스로 만들지 않는다

**작업을 시작할 때 세션은 지금 체크아웃돼 있는 브랜치에서 일한다.** 새 브랜치가 필요하다고 판단되면 만들기 전에 **브랜치 이름과 PR 제목을 먼저 보여 주고 승인을 받는다.**

이 조항이 이름 규칙과 한 문서에 있는 이유가 있다. 이름을 아무리 잘 정해도 **사용자가 모르는 사이에 브랜치가 생기면** 그 사람의 목록에는 여전히 설명 없는 가지가 늘어난다. 규칙이 막으려는 것은 나쁜 이름이 아니라 **"이게 언제 왜 생겼지"** 이고, 그것은 이름만으로 막히지 않는다.

예외가 하나 있다. **클라우드(웹) 세션은 플랫폼이 `claude/...` 브랜치를 자동으로 만들므로 이 조항의 적용 밖이다.** 그쪽은 머지 직후 브랜치를 지우는 것으로 정리한다.

## 4. 브랜치 하나 = PR 하나, 머지되면 지운다

- 한 브랜치에 여러 작업을 얹지 않는다. 얹으면 PR 이 커져 리뷰가 어려워지고, 하나가 막히면 나머지가 함께 막힌다.
- **머지된 브랜치는 지운다.** 남겨 두면 다음 사람이 "이건 아직 안 끝난 건가"를 매번 확인해야 한다. GitHub 저장소 설정의 자동 삭제를 켜 두면 사람이 기억할 필요가 없다.
- **한 브랜치를 두 곳에서 동시에 열지 않는다.** 같은 것을 두 세션이 나란히 고치면 뒤의 것이 앞의 것을 조용히 되돌린다 — 오류가 나지 않아 발견이 늦다.

## 5. 봇이 만드는 브랜치는 이 규칙 밖이다

동기화 봇 같은 자동 장치가 만드는 브랜치(`chore/sync-warehouse` 등)는 **이름이 고정돼 있고 매번 같은 브랜치를 다시 쓴다.** 사람이 이름을 고르는 자리가 없으므로 3절이 적용되지 않고, 쌓이지도 않는다. 다만 종류 접두어는 위 여섯 중 하나를 쓴다.

## 적용 범위

- 모든 저장소의 모든 세션에 적용된다. 저장소의 `CLAUDE.md` 에 더 구체적인 이름 규칙이 있으면 그것이 이긴다.
- 단일 원본은 창고(Template-repository)의 `.claude/rules/branch-pr-naming.md` 다. 여기서만 고치고, 동기화 봇이 내려보낸다.
