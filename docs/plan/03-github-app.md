# 1단계 세 번째 단위 — GitHub App 으로 진짜 저장소를 읽는다

> 한 줄 요지: **사용자가 만든 GitHub App 의 설치 토큰으로, 설치된 저장소들의 PR 을 읽기 전용으로 가져온다.** 이 단위가 끝나면 1단계의 성공 기준 "저장소 5개 이상의 PR 을 혼동 없이 업무에 보이기" 를 실제 데이터로 확인할 수 있다. 결정 11 을 코드로 옮긴다.

## 1. 사람이 하는 일과 코드가 하는 일

| 누가 | 무엇을 | 어디서 |
|---|---|---|
| 사용자 | GitHub App 을 만들고, 읽을 저장소에 설치하고, 비밀 키 파일을 받는다 | GitHub 설정 화면 (브라우저) |
| 사용자 | App ID · 설치 ID · 비밀 키 파일 경로를 `.env.local` 에 적는다 | 앱을 띄울 컴퓨터 |
| Studio | 비밀 키로 JWT(App 이 자기임을 증명하는 짧은 서명)를 만들고, 설치 토큰으로 바꾼다 | 서버 |
| Studio | 설치 토큰으로 설치된 저장소 목록과 각 저장소의 PR 을 GET 으로 읽는다 | 서버 |

## 2. 읽기 전용 경계가 한 곳 넓어진다

설치 토큰을 받는 요청(`POST /app/installations/{id}/access_tokens`)은 GitHub 의 규칙상 POST 다. 저장소의 상태를 바꾸는 요청이 아니라 **인증 요청**이다. 그래서 경계를 이렇게 나눈다.

- **인증 모듈** 하나만 이 POST 를 보낼 수 있다. 주소 모양 · 호스트 · 본문(권한을 더 좁히는 요청만)을 모두 고정하고, 다른 POST 는 보내기 전에 막는다.
- **데이터 리더**는 지금처럼 GET 만 보낸다. 인증 모듈이 준 토큰을 받아 쓸 뿐, POST 를 보내는 길이 없다.
- 설치 토큰을 요청할 때 권한을 **읽기로만** 좁혀 달라고 적는다. App 에 실수로 쓰기 권한이 켜져 있어도 Studio 가 받는 토큰은 읽기뿐이다.

## 3. 범위

| 들어가는 것 | 들어가지 않는 것 |
|---|---|
| App 인증: 비밀 키로 JWT 서명(Node 내장 `crypto`, 새 라이브러리 없음), 설치 토큰 교환과 만료 전 갱신 | 웹훅 수신 (공개 주소가 생긴 뒤) |
| 설치된 저장소 목록 읽기. `GITHUB_REPOS` 가 없으면 설치된 저장소 전부, 있으면 그중 적힌 것만 | 여러 설치(조직 여러 개) 동시 지원 |
| PR 목록 페이지 넘김. 저장소마다 열린 PR 전부와 최근 닫힌 PR 일부. 상한은 화면에 밝힌다 | 쓰기 권한이 필요한 모든 것 |
| Inbox 는 열린 PR 만. 연결 안 된 닫힌 · 병합된 PR 은 개수만 | 배포 위치 |
| 화면 출처 표시 "GitHub App" 과 마지막 Sync 결과(읽은 저장소 수 · PR 수 · 실패) | |
| 사람용 설정 안내 [`docs/setup/github-app.md`](../setup/github-app.md) | |

## 4. 통과 기준

1. 비밀 키와 App ID 로 만든 JWT 가 GitHub 의 규격(RS256, 발급 시각 60초 전 · 만료 10분 이내)을 지키고, 설치 토큰 교환 요청이 읽기 권한만 요청한다. 가짜 GitHub 응답으로 시험한다.
2. 인증 모듈 밖에서는 POST 를 보낼 수 없고, 인증 모듈도 정해진 주소 외에는 POST 를 보내지 못한다. 시험이 둘 다 확인한다.
3. 설치 토큰이 만료되기 전에 새로 받고, 만료된 토큰으로 401 을 받으면 한 번만 다시 받아 재시도한다.
4. 비밀 키 · JWT · 설치 토큰이 로그 · 오류 · 화면 · 저장소 파일에 나오지 않는다. 비밀 키 파일 경로만 설정에 적는다.
5. Inbox 에는 열린 PR 만 보이고, 연결 안 된 닫힌 · 병합된 PR 은 개수로만 보인다.
6. 앞선 두 단위의 시험이 계속 통과한다.
7. 사용자가 App 을 설치한 뒤 **실제 저장소로 Sync 해 PR 이 업무 · Inbox 에 나타나는 것**을 확인한다. 이것은 사용자의 컴퓨터(또는 비밀 키가 있는 환경)에서만 가능하므로, 확인 전까지 이 단위의 보고에 "실데이터 미확인" 을 붙인다.

   **확인됨 (2026-09-28).** 사용자의 Windows PC 에서 App 만 설정하고(조직 토큰 없이) 메모리 모드로 띄웠다. 위쪽 띠에 `GitHub App (read-only)` 와 `저장소 17 · PR 102` 가 보였고 오류는 없었다. 저장소 17개가 프로젝트로 나왔고, Inbox 에는 연결을 기다리는 열린 PR 7개가 있었다. 한 번의 Sync 는 86~103초 걸렸다. 조직 토큰을 함께 쓰는 경로(결정 12)는 아직 실데이터로 확인하지 않았다.

## 5. Sync 속도 (실측 뒤 고친 것)

위 실측의 86~103초는 요청 수가 아니라 **요청을 하나씩 차례로 보낸 것**이 원인이었다. 저장소 17개 · PR 102개를 App 으로 읽으면 요청은 239번(설치된 저장소 목록 1 + 저장소마다 PR 목록 2 + PR 마다 검사 · 리뷰 2)이고, 요청 하나에 0.4초가 걸리면 차례로 보낼 때 약 96초가 된다. 지연을 넣은 가짜 GitHub 로 재서 확인했다(`tests/unit/sync-speed.test.ts`, 요청 지연은 `SYNC_BENCH_LATENCY_MS` 로 바꾼다).

그래서 요청을 겹쳐 보낸다. 규칙은 이렇다.

1. 한 번의 Sync 에서 동시에 나가 있는 요청은 **8개까지**다(`MAX_CONCURRENT_REQUESTS`). 요청 예산 하나를 나눠 쓰는 모든 출처가 이 상한도 함께 나눠 쓴다. GitHub 는 동시 요청을 많이 보내면 보조 속도 제한(secondary rate limit)을 건다고 안내하므로 작게 둔다.
2. PR 마다의 검사 · 리뷰 요청은 겹쳐 보낸다. 저장소마다의 **PR 목록** 요청만은 저장소 순서대로 하나씩 보낸다 — 앞 저장소의 목록이 실패하면(예: 조직이 토큰을 막았다) 같은 출처의 다음 저장소는 부르지 않던 규칙을 그대로 지키기 위해서다.
3. 한 출처의 요청 하나가 실패하면 그 출처의 줄 서 있던 요청은 보내지 않는다. 다른 출처는 계속 읽는다.
4. 요청 수 · 요청 상한(1500) · GET 만 · 401 재시도 규칙은 바뀌지 않았다. 받아 적는 순서도 저장소 순서 그대로다.

같은 조건(요청 지연 0.4초, 저장소 17개 · PR 102개, App 만)에서 **95.97초가 14.54초**가 됐다. 요청 수는 239번 그대로다. 사용자 PC 에서는 아직 다시 재지 않았다.
