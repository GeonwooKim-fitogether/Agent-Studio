Agent Studio · 사용자 워크플로우 중심 개발 기획안

어디서 시작하든,
GitHub의 PR에서 만나기

여러 프로젝트를 Claude 클라우드, 로컬, 동료와 병렬로 진행해도 업무의 맥락과 코드의 현재 상태를 다시 찾느라 헤매지 않는 제품. 사용자는 Studio에서 “지금 무엇을 확인할지” 결정하고, 실제 코드와 병합 상태는 GitHub에서 확인한다.

현 상태 화면과 클릭 흐름을 보여주는 시안 → 첫 목표 GitHub 실연동 + PR 1개 원격 미리보기
설계 원칙누가 · 어디서처음 연결매일의 흐름화면과 동작나중의 AI 실행개발 순서
01 · 원칙

사용자에게 필요한 것은 한 가지 흐름

업무의 단위

프로젝트 안의 업무

업무 하나에 대화, 외부 작업 링크, 관련 PR 여러 개, 검토 결정이 모인다. 다른 곳에서 시작한 PR도 같은 업무에 연결할 수 있다.

코드의 기준

GitHub의 PR

브랜치, PR, 검사 결과, 승인, 병합은 GitHub의 상태를 보여준다. Studio의 “검토 완료”는 GitHub 병합을 대신하지 않는다.

실행의 장소

클라우드 또는 Mac Pro

코드 작업은 어디서 시작하든 된다. 실제 앱 확인이 필요할 때 Mac Pro가 선택한 PR의 특정 커밋을 실행하고, 사용자는 다른 기기에서 미리보기를 연다.

02 · 역할

누가 · 어디에서 · 무엇을 · 왜

누가어디에서무엇을왜
사용자Studio · 노트북/휴대폰프로젝트와 업무를 만들고, PR 연결·검토·다음 행동을 결정5개 이상 프로젝트의 맥락을 한눈에 되찾기 위해
사용자 또는 동료Claude 클라우드 또는 로컬 개발 환경코드를 만들고 GitHub에 PR을 올림장소에 얽매이지 않고 병렬로 개발하기 위해
GitHub연결된 저장소PR·커밋·검사·리뷰·병합의 현재 상태를 보관팀 모두가 같은 코드 기준을 보기 위해
Agent Studio웹 서비스연결된 저장소의 PR을 읽어 업무에 표시하고, 연결이 모호한 항목을 Inbox에 제시외부 AI 세션과 브랜치가 흩어져도 업무를 잃지 않기 위해
Mac Pro켜져 있는 로컬 실행 기기선택한 PR의 커밋으로 앱을 실행하고 접근이 제한된 미리보기를 제공밖에서도 실제 화면과 서버 동작을 확인하기 위해

연결된 AI 모델은 다음 단계의 “Studio에서 실행” 기능에 참여한다. GitHub PR 모으기와 미리보기에는 AI 모델 연결을 요구하지 않는다.

03 · 최초 설정

처음에는 두 가지만 연결

사용자는 개발 설정 전체를 한 번에 배우지 않는다. PR 모으기를 먼저 켜고, 화면 검증이 필요할 때 실행 기기를 연결한다.

1 · 사용자 / Studio

GitHub 저장소 선택

이 프로젝트가 읽어야 할 저장소를 지정한다. 초기 권한은 PR과 검사 상태를 읽는 데 필요한 범위로 제한한다.

2 · Studio / GitHub

기존 PR부터 가져오기

이미 만들어진 PR도 프로젝트에 나타난다. 업무를 확실히 알 수 없는 PR은 Inbox에 남기고 사용자가 연결한다.

3 · 사용자 / Mac Pro

미리보기 기기 연결

선택한 PR 1개를 실행할 수 있는지 노트북과 휴대폰에서 확인한다. 기기가 꺼지면 PR 확인은 계속 가능하고 미리보기만 멈춘다.

연결 원칙. 외부에서 이미 생성된 PR을 Studio의 업무에 잘못 붙이지 않는다. “프로젝트의 새 PR”로 먼저 보이고, 관계가 불분명하면 사용자가 Inbox에서 기존 업무에 연결하거나 새 업무를 만든다.

04 · 매일의 흐름

시작 장소가 달라도 같은 곳으로 돌아온다

아래는 사용자가 실제로 경험할 순서다. 각 카드의 오른쪽은 그 단계가 일어나는 장소다.

① 업무를 연다

사용자 · Studio / 어디서든

목적과 연결할 프로젝트를 적는다. 왜: 다른 AI 세션으로 이동해도 동일한 업무로 돌아오기 위해.

② 코드를 작업하고 PR을 만든다

사용자·동료 · 클라우드/로컬 → GitHub

Claude 클라우드, 로컬 또는 동료의 환경에서 개발한다. 왜: 병렬 작업과 팀 협업을 한 방식으로 묶기 위해.

③ Studio가 PR 상태를 읽는다

Studio ↔ GitHub

저장소·PR 번호·최신 커밋·검사 결과를 가져온다. 왜: 세션이 바뀌어도 실제 코드 위치와 현재 결과를 확인하기 위해.

연결이 분명함해당 업무의 Chat과 Workspace에 PR을 표시
연결이 불분명함Inbox에서 “업무에 연결 / 새 업무 만들기” 선택

④ 결과를 확인한다

사용자 · Workspace → Chat

무슨 업무인지, 어떤 PR인지, 검사와 리뷰가 어디까지 왔는지 한 카드에서 본다. 왜: GitHub 탭과 AI 세션을 일일이 뒤지지 않기 위해.

⑤ 화면 검증이 필요하면 미리보기를 연다

Mac Pro 실행 → 사용자 기기에서 보기

선택한 PR의 특정 커밋을 실행한다. 미리보기에 PR 번호와 커밋을 함께 표시한다. 왜: 자신이 본 화면과 검토 중인 코드가 일치하도록 하기 위해.

⑥ 다음 행동을 결정한다

사용자 · Studio Review → GitHub

Studio에는 “수정 요청” 사유 또는 “내부 검토 완료”를 기록한다. 수정 내용을 동료에게 전달하거나 공식 리뷰·병합을 할 때는 GitHub PR로 이동한다. 왜: 내부 기록과 실제 팀 알림·코드 반영을 혼동하지 않기 위해.

⑦ 결과가 다시 반영된다

GitHub → Studio

새 커밋, 검사 실패, PR 병합이 해당 업무에 반영된다. 왜: 나중에 어느 기기에서 열어도 최신 상태를 이어서 보기 위해.

미리보기의 예외. PR에 새 커밋이 들어오면 이전 화면은 “이전 버전”으로 표시하고 검토 근거로 쓰지 않는다. 사용자가 최신 커밋으로 다시 실행한다. 첫 버전에서 다른 PR을 실행하면 이전 미리보기를 종료하고 알려준다. Mac Pro가 꺼져 있으면 원인과 재연결 행동을 보여준다.

05 · 화면 연결

기존 화면에서 어떤 버튼이 실제로 해야 할 일

현재 화면 / 행동사용자가 기대하는 결과개발 시 연결할 동작
Workspace · 업무 열기그 업무의 최근 PR과 다음 행동 확인업무 ID로 Chat 열기; 연결된 PR 및 검사 상태 함께 조회
Chat · GitHub PR 열기실제 코드를 확인연결된 저장소와 PR 번호의 GitHub 페이지 열기
Chat · 미리보기 시작지금 선택한 PR의 실제 화면 확인Mac Pro 가용 상태 확인 → PR의 최신 커밋 고정 → 실행/접근 제한 → 주소와 커밋 표시
Inbox · 연결하기떠 있는 PR을 올바른 업무에 정리저장소 ID+PR 번호를 선택 업무에 연결; 모호하면 자동 추측하지 않기
Review · 수정 요청 / 검토 완료결정을 남기고 후속 행동 확인업무에 내부 결정을 저장하고 GitHub PR로 가는 행동 표시; 팀 알림·공식 리뷰·병합을 자동 수행한 것처럼 표시하지 않기
Flow · 단계 편집필요할 때만 작업 순서 변경기본 PR 추적 흐름에는 요구하지 않음; 향후 Studio 실행 설정으로 사용
Agents · 이름 / 소개 / 지시문 / 모델AI 역할을 정확히 지정소개는 사람이 읽는 설명, 지시문은 실행 프롬프트; 실제로 연결·확인된 모델만 선택 가능

현재 HTML 시안의 버튼과 모델 목록은 동작을 설명하는 예시다. GitHub 연동·Mac Pro 실행·AI 실행은 아직 실서비스 기능으로 구현되지 않았다.

06 · 다음 단계

Studio에서 AI를 실행하는 흐름은 그 다음

먼저 외부 PR도 놓치지 않는 흐름을 검증한다. 그다음 연결된 모델로 Studio가 직접 작업을 시작하는 기능을 붙인다.

① Agent를 준비한다

사용자 · Agents

이름과 소개(사람이 읽는 설명), 지시문(AI에 전달할 프롬프트), 필요한 스킬, 실제 연결된 모델을 고른다.

② 업무에서 실행한다

사용자 · Chat / Flow

프로젝트 저장소와 목표를 확인하고 Run을 누른다. 연결이 끊긴 모델이거나 실행 경로가 검증되지 않았다면 실행할 수 없게 표시한다.

③ 결과는 같은 PR 흐름으로 돌아온다

AI 실행 환경 → GitHub → Studio

사용한 모델·지시문 버전·작업 결과를 업무에 남기고, 코드 변경은 PR로 검토한다. 앞의 ③~⑦ 단계를 그대로 쓴다.

모델 표시 기준. 사용자의 연결에서 실제 이용 가능한 모델을 확인한 뒤 선택지로 제시한다. 예시 모델 이름을 “연결 완료”처럼 보여주거나 실행 가능한 척하는 Run 버튼을 두지 않는다.

07 · 개발 순서

첫 제품은 작은 검증을 이어 붙인다

0 · 계약 정의

한 업무와 한 PR

업무 ID와 저장소 ID·PR 번호·최신 커밋의 관계를 정한다. Studio 검토 상태와 GitHub PR 상태를 별도로 정의한다.

확인: 같은 이름의 브랜치라도 다른 저장소 PR과 섞이지 않는다.

1 · 첫 배포 범위

5개 이상 저장소의 PR 모으기

읽기 권한으로 기존 PR을 불러오고 변경을 반영한다. Claude 클라우드나 동료가 Studio 밖에서 만든 PR도 보이며, 연결이 모호하면 Inbox로 간다.

확인: 외부 PR을 기존 업무 또는 새 업무에 연결할 수 있고 병합 상태가 다시 반영된다.

2 · 원격 검증

Mac Pro에서 PR 1개 미리보기

PR의 특정 커밋을 격리해 앱을 실행하고, 접근이 제한된 링크를 노트북·휴대폰에서 연다. 첫 버전의 동시 미리보기는 1개로 제한한다.

확인: PR 갱신 또는 Mac Pro 연결 끊김 때 이전 미리보기를 최신으로 오해할 수 없다.

3 · 확장

연결된 AI 모델로 Studio Run

제공자별 이용 가능한 모델 확인과 공식 실행 경로를 검증한다. Agent 지시문·스킬·모델 선택을 실제 실행과 PR 결과에 연결한다.

확인: 모델 미연결 시 Run 차단, 실행 이력과 결과 PR이 같은 업무에 남는다.

출시 판단: 사용자가 직접 따라 해볼 시나리오
  • 저장소 5개를 연결하고, Studio 밖에서 만든 PR을 찾아 기존 업무에 연결한다.
  • 업무 카드에서 PR·검사 결과를 보고, 선택한 PR의 커밋을 Mac Pro에서 열어 휴대폰으로 확인한다.
  • PR에 새 커밋이 오면 이전 미리보기가 오래된 것으로 표시되고 새 버전을 다시 연다.
  • Studio의 “내부 검토 완료”와 GitHub의 실제 리뷰·병합 상태가 혼동되지 않는다.

설계 근거: GitHub App 웹훅 · GitHub App 권한 · PR API. Mac Pro 원격 미리보기와 AI Run의 구체적인 방식은 시범 연결에서 검증할 설계안이다.
